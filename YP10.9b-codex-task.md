## Objective

## Required regressions

- Price changed then reverted to confirmed value: desired counter increases; effective pending=false; Publish Changes disabled; direct API publish rejects without remote calls.
- Quantity +1 then -1: same; cumulative counter matches confirmed despite advanced desired revision.
- Price and quantity changed then both reverted; then restaged to genuinely different values: effective pending=true again, original confirmed baseline remains intact.
- Partial revert (e.g., price reverted but quantity remains +1): still pending.
- New variation, removed variation, representative image/copy change, selector/title/description/group settings, copy availability and pending permanent-removal marker: still pending.
- Missing/malformed confirmed snapshot or group/identity mismatch: never falsely report no pending changes.
- Support both initial v1 and active v3 confirmed snapshots, no accidental differences from normal publish lifecycle or timestamp-only updates.
- Frozen/recovery cases preserve existing safety and button semantics.
- Validate frontend readiness behavior on pending true/false; avoid unrelated UI refactoring.
