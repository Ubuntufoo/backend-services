# ROADMAP — VARIATION LISTINGS

This roadmap is intentionally separate from `ROADMAP.md`. The variation listing is a dedicated Inventory API variation-group workflow, not a third legacy Single/Lot capture type. Backend and frontend work must remain isolated from existing Single and Lot contracts unless a roadmap task explicitly says otherwise.

The `YP0`–`YP9` task IDs are retained as roadmap provenance. Likewise, `YPSBX-*` Sandbox keys,
recorded listing/resource IDs, `.local/you-pick-sandbox/**` manifests, and the
`ebay-ui-app-you-pick` worktree name remain historical or repository identifiers; they are not the
current variation-listing production namespace.

## Current product and service understanding

- One buyer-facing eBay listing is represented by one `InventoryItemGroup` plus the complete set of child inventory items and offers. Application-owned selector order is authoritative; Sandbox reads proved that eBay may return group `variantSKUs` in a different order, so remote reconciliation requires exact membership rather than response-order equality.
- One aggregate is identified by an immutable application UUID and owns ordered variations, each with its own immutable application UUID. Remote group keys/SKUs are deterministic namespaced projections of those IDs and remain distinct from offer, listing, and opaque Media identities.
- Each selectable card owns an immutable variation SKU, one eBay child inventory item, one offer, one immutable canonical selector value, one price, a desired quantity derived from eligible physical copies, and one representative ordered front/back image pair.
- The group owns title, description, category, marketplace, merchant location, business policies,
  the derived common eBay-aspect projection, selector definition, and one shared condition
  tier/descriptors. Each variation also retains application-owned card metadata.
- Every variation in a group must satisfy the same selected condition contract. A card needing another condition belongs in another group.
- The selector aspect/value is repeated consistently between group `variesBy` and child `product.aspects`. The Sandbox-proven MVP image arrangement uses seller-owned EPS URLs on each child `product.imageUrls` as ordered `[front, back]`, keeps `aspectsImageVariesBy` on the selector, and omits group-level `imageUrls`; group pivots produced unbound duplicate buyer images.
- External source images must be ingested through the current eBay Media API before publication. Media resource IDs are opaque eBay identifiers and must not be constrained by a locally invented character alphabet; trust comes from exact HTTPS eBay host/path and URI safety checks.
- Current Media integration has no image-delete operation. Unused EPS resources are preserved as expiring evidence rather than treated as Inventory cleanup targets.
- Group replacement is always a complete snapshot. Omission-based patching is unsafe.
- Listings created through Inventory API must continue to be managed through Inventory API; Trading API is used only for the narrow Sandbox identity proof already documented.
- Publication is group-scoped. Pricing, quantity, order reconciliation, and sold history are variation-SKU-scoped. Setting one variation quantity to zero removes that selector from buyer view while remaining in-stock variations stay purchasable.
- A zero-quantity variation does not need to be restored before withdrawal and exact unsold cleanup; the successful Sandbox run was withdrawn and deleted directly from the zero-quantity state.
- Manifest publication/listing/offer identities are durable historical ownership facts after cleanup; current remote absence is represented separately by cleanup state, terminal absence evidence, and lifecycle reconciliation.
- The observed reference listing exposed 87 selector values, but this does not establish a universal API or operational limit. The initial application-service admission cap is configurable to 2 or 3 variations (default 2) until recorded scale evidence justifies expansion.
- The frontend requires a separate variation listing workspace. It must not reuse the singular Single/Lot listing state machine or capture selector.
- The frontend must expose variation listing as a clear alternate listing mode/workspace so the user deliberately enters a distinct workflow rather than treating it as a variation of the standard Single/Lot editor.
- Variation listing pricing is fully manual. Each variation card is assigned exactly one of four fixed price baskets: `$0.99`, `$1.49`, `$1.99`, or `$2.49`. The workflow must optimize for fast repeated intake through one-click/low-friction tier selection.
- Variation listing generation must not call SoldComps or the eBay Browse API for pricing or market discovery. Gemini is the only AI/model provider used by the variation listing generation pathway; pricing remains operator-selected and deterministic.
- Category `261328` item-specific ownership follows the corrected YP1.4 contract: variation-specific
  Gemini/reviewed metadata may differ; `InventoryItemGroup.aspects` contains only a derived,
  truthful value/set common to every variation; and only the proven custom `Card` selector varies per
  variation. Optional/recommended heterogeneous aspects are omitted from eBay, required no-common
  aspects block or require regrouping, and arbitrary extra variation aspects remain forbidden as
  hidden metadata or additional pivots.
- No production eBay write is authorized by implementation, tests, Sandbox success, or database readiness alone.
- The initial additive variation-listing persistence migration was applied exactly once through the canonical linked Supabase workflow in YP2.4. The four namespaced tables are present in production and were verified empty immediately after apply; critical existing Single/Lot schema and data remained unchanged.
- The variation listing worktree and canonical `backend-services` use the same hosted Supabase database; Git/worktree isolation does not isolate database state.
- Future shared database mutations remain separate authorization gates. YP2.6 applied only the reviewed lightweight publishing-journal migration; it does not authorize any later hosted write.
- This is a private, single-user application. Architecture should optimize for a small maintainable codebase, not hypothetical multi-tenant or large-scale commercial requirements. Keep only safeguards justified by real local corruption risk or ambiguous external eBay mutations; do not build generic workflow engines, event sourcing, generalized audit systems, or speculative concurrency infrastructure.

## Task sizing and execution routing

For unfinished roadmap rows, **direct ChatGPT implementation is preferred whenever the task can be safely completed through the available repo tools with focused review/validation**. Fallback routing depends on task complexity and execution surface. Bounded lower-complexity work that does not require direct Docker, Supabase CLI/MCP, or PostgreSQL interaction may use `ChatGPT + DeepSeek fallback`. Highly complex work, architecture-sensitive/recovery work, or anything that directly exercises Docker, Supabase, or PostgreSQL through CLI/MCP uses `ChatGPT + Codex fallback`. **Unmarked (`—`) unfinished tasks are assumed to go directly to Codex**, which remains the default for broader autonomous command execution, ambiguous external-state handling, destructive recovery logic, or other high-risk/problem-solving-heavy implementation. Completed Phase 0/Phase 1 model labels are retained as historical provenance and do not control future delegation.

- **ChatGPT + DeepSeek fallback:** Use for bounded, lower-complexity implementation that stays within normal repository code/tests and does not require direct Docker, Supabase CLI/MCP, PostgreSQL, hosted database, or architecture-sensitive recovery work. ChatGPT should implement directly when practical; DeepSeek is the fallback when ordinary local execution/validation is needed.
- **ChatGPT + Codex fallback:** Use when ChatGPT can reasonably attempt the bounded work but the fallback requires stronger autonomous problem-solving, multi-step integration, concurrency/recovery reasoning, or direct Docker/Supabase/PostgreSQL tooling. Codex is the fallback rather than DeepSeek for these tasks.
- **`—` / unmarked unfinished task:** Codex is assumed/default; no special label is needed.
- **Operator + Sol review:** live eBay/database execution or buyer-facing manual verification; explicit authorization is still required.

Prefer assigning ChatGPT directly rather than delegating merely for convenience. Keep DeepSeek on bounded lower-complexity work without database/container tooling; use Codex whenever complexity, database tooling, or recovery semantics materially increase implementation risk. Do not split tasks solely to maximize use of any particular agent.

### Private single-user sizing principle

Prefer the smallest design that safely supports one operator and this application's actual workflows. Database structure should enforce durable identity, relational integrity, and unsafe-replay boundaries; straightforward TypeScript service code may own lifecycle decisions that do not require database enforcement. Do not normalize immutable execution snapshots merely for theoretical extensibility. JSONB is acceptable for frozen revision/request/read-back evidence when relational querying is not an actual product requirement. Add tables, checkpoints, and constraints only when they prevent a demonstrated failure mode or are required by an immediately downstream feature.

## Permanent constraints

- One shared eBay condition contract per group; no mixed-condition publication.
- Physical copies may carry different internal conditions, but every copy counted as available for one variation must remain compatible with the group's shared eBay condition contract.
- Variation listing groups are long-lived inventory buckets that may receive new variations and duplicate-copy replenishment after publication; local changes are staged and synchronized only through explicit batch publication/revision.
- One variation represents one eBay variation/SKU. Multiple physical duplicates are `variation_listing_copies` under that variation and derive its desired quantity; duplicate copies never create duplicate selectors/SKUs.
- Every physical copy owns its own front/back R2 image pair under immutable group/variation/copy identity. Exactly one copy is the variation's representative image source for eBay; selling that copy does not automatically change the representative image.
- variation listing intake uses an explicit sticky target group and sticky price tier plus an explicit duplicate-copy mode; it must not be added to or inferred through the legacy Single/Lot capture-mode machinery.
- Variation listing SKUs extend the app's existing structured inventory SKU convention for easier physical order pulling: the category prefix and six-digit inventory serial retain their existing range/formatting, while the middle segment becomes a stable variation-listing bucket token such as `McGrady` or `2003Topps`. Each retained `(category, bucket token)` namespace is unique; its locked group allocator consumes serials monotonically and fails closed at overflow. Complete application-owned variation SKUs are unique. Existing Single/Lot latest-plus-collision allocation, parsing, output, and SKU behavior remain unchanged.
- variation listing is a deliberately separate application mode/workspace from standard Single/Lot listing creation.
- Variation pricing is fully manual and restricted to the four fixed baskets `$0.99`, `$1.49`, `$1.99`, and `$2.49`; no SoldComps, eBay Browse pricing, market-derived repricing, or automatic pricing call is part of the variation listing pathway.
- Gemini is the only AI/model provider in the variation listing generation pathway. Gemini may generate identity/review/group content, but it does not choose or alter the manual variation price tier.
- Shared-vs-variation item-specific ownership must follow the corrected YP1.4 category `261328`
  contract: persist variation-specific Gemini/reviewed metadata separately; derive
  `InventoryItemGroup.aspects` only from truthful values common to every variation; omit heterogeneous
  optional/recommended values; block or regroup when required aspects lack a common value/set;
  and permit only the proven custom `Card` selector to vary across eBay child variations. No implementation
  may place arbitrary extra variation aspects into Inventory payloads or invent buyer-facing pivots.
- One immutable application UUID and canonical selector identity/value per variation. Each variation also owns one immutable structured inventory SKU using `<category-prefix>-<bucket-token>-<six-digit-inventory-serial>`; duplicate physical copies share that SKU. Selector labels do not encode stock, price, position, SKU serial, or UI-only suffixes.
- Group identity is an immutable application UUID; `VL-G-<GROUP_UUID_HEX>` is its distinct remote Inventory key. Offer IDs, listing IDs, and opaque Media IDs/URLs remain separately owned historical identities.
- Complete group snapshots only; no omission-based group patching.
- Selector ordering is application-owned through the declared selector values; eBay-returned group `variantSKUs` are reconciled as exact membership and must not be treated as authoritative order.
- Published variation listing images use seller-owned EPS URLs on each eBay child inventory item in deterministic `[front, back]` order; group-level `imageUrls` are omitted for the accepted variation-only arrangement.
- Media resource IDs are opaque; validate trusted eBay resource URI boundaries rather than an invented identifier alphabet.
- Quantity zero is the supported way to make one variation unavailable without disrupting remaining variations; cleanup must support the zero-quantity state without requiring restoration.
- Order/sold evidence permanently protects variation identity and history from destructive erasure; unresolved variation/order matching fails closed until YP8.1/YP8.2.
- Published groups require withdrawal before Inventory cleanup; abandonment applies only before buyer-facing publication or when exact reads prove no withdrawal is required.
- Inventory cleanup does not imply Media deletion. EPS resources outside Inventory ownership are allowed to expire under the current Media API lifecycle.
- Inventory API owns all listing mutations after creation.
- Exact read-before-write recovery; unknown remote state never authorizes replay or destructive cleanup.
- Existing Single and Lot intake, generation, pricing, publishing, reconciliation, deletion, routes, and SKU grammar remain unchanged.
- Publishing recovery is a small crash-safe journal, not an enterprise audit platform: freeze one Publish Changes revision, journal only the remote operations/evidence needed for safe resume, preserve retry truth, and stop on unknown state. Do not add generic event sourcing, workflow engines, remote-resource registries, observation timelines, multi-tenant ownership, or speculative worker-concurrency infrastructure.
- Prefer JSONB for immutable revision/request/read-back snapshots when no product query requires normalization; keep relational columns for identity, ownership, ordering, status, timestamps, foreign keys, and uniqueness that prevent real corruption.
- Sold/order persistence is intentionally deferred until YP8.1 proves the real eBay order-line contract; do not pre-build order-history schema in Phase 2.
- Initial local persistence is exactly `variation_listing_groups`, `variation_listing_variations`, `variation_listing_copies`, and `variation_listing_intake_sessions`; no session state lives on groups and no manual quantity column exists. YP2.5 adds only the minimal separate publishing-journal state needed for frozen revisions and safe remote recovery.
- No hosted database migration or data write may be inferred from a completed coding task. YP2.4 and YP2.6 are complete; every later hosted migration application still requires separate explicit authorization.
- Shared Supabase changes are applied once through the canonical migration workflow; never independently from both worktrees.
- Before the first shared migration, all database validation uses local or disposable infrastructure. Feature-branch code must not write experimental rows into canonical tables.
- No raw `.local/you-pick-sandbox/**` artifact is committed. Only sanitized durable conclusions belong in tracked documentation.
- No production write occurs without a separate explicit authorization after all preceding gates pass.
