# ROADMAP — VARIATION LISTINGS

This roadmap is the authoritative task ledger for the dedicated Inventory API variation-listing workflow. It is separate from legacy Single/Lot; task IDs (`YP0`–`YP9`), `YPSBX-*`, `.local/you-pick-sandbox/**`, and worktree names are retained only as historical/repository provenance. Detailed product invariants are consolidated under **Permanent constraints** instead of repeated before the task tables.

## Execution routing

| Label | Use |
| --- | --- |
| `ChatGPT + DeepSeek fallback` | Direct ChatGPT preferred; DeepSeek only for bounded repo/code/test execution without DB/container/recovery complexity. |
| `ChatGPT + Codex fallback` | Direct ChatGPT may start; Codex handles architecture/recovery/concurrency or Docker/Supabase/PostgreSQL execution. |
| `Terra (high) + Codex` | Prefer for bounded, lower-complexity repo implementation/review/test slices with clear acceptance criteria and no live eBay or hosted-database mutation; use as the token-efficient Codex orchestrator when Sol-level integration reasoning is unnecessary. |
| `—` | Codex default for unfinished work. |
| `Operator + Sol review` | Live eBay/database execution or buyer-facing verification; explicit authorization required. |

**Sizing:** private single-user app; prefer the smallest maintainable design. Add persistence/checkpoints/constraints only for demonstrated corruption/replay risks or immediate downstream requirements; JSONB is appropriate for immutable evidence that is not queried relationally.

## Permanent constraints

- **Coexistence / isolation:** Standard Single/Lot listing creation is an equally important first-class daily workflow and remains unchanged in ownership, UI behavior, intake, generation, pricing, publishing, reconciliation, deletion, routes, allocation, and SKU grammar. Variation Listings is a parallel alternate mode for grouped inventory and replenishment, not a replacement, parent workflow, or shared lifecycle for Standard listings. Both modes must coexist without cross-mode state, capture, SKU, pricing, or publication interference.
- **Group/condition:** one shared eBay condition contract per group. Copies may retain different internal conditions only when compatible with that shared contract; mixed-condition publication is forbidden.
- **Inventory model:** groups are long-lived buckets. One variation = one immutable selector + SKU; duplicate physical copies share it. Before initial publication, quantity is derived from eligible captured copies. After publication, eBay is authoritative for current sellable quantity. Local post-publication quantity intent is represented only by a cumulative variation-level adjustment counter; the delta from the previous confirmed counter is applied to a **fresh** remote eBay sellable baseline during explicit **Publish Changes**. Captured copy-row count/availability is historical/intake evidence, not live inventory authority and never identifies which copy sold.
- **Copies/images:** each copy owns immutable group/variation/copy front/back R2 identity; exactly one copy is representative and selling it does not auto-switch the representative. Published child images are seller-owned EPS `[front, back]`; omit group-level `imageUrls`.
- **Intake:** explicit sticky target group + sticky manual tier + duplicate-copy mode; never infer variation intake through Single/Lot capture state.
- **SKU/identity:** immutable group UUID → `VL-G-<GROUP_UUID_HEX>` remote key; immutable variation UUID/selector and `<category-prefix>-<bucket-token>-<six-digit-serial>` SKU. `(category,bucket)` namespaces are unique, allocation is monotonic/fail-closed, duplicates share SKU, and selector labels contain no stock/price/position/serial/UI suffixes. Offer/listing/Media identities remain separate historical facts.
- **Pricing/AI:** only nine manual tiers `$0.99/$1.49/$1.99/$2.49/$2.99/$3.49/$3.99/$4.49/$4.99`; no SoldComps/Browse/market/automatic repricing. The operator-approved nine-tier Supabase migration was applied 2026-09-23; matching FE/BE runtime deployment remains a separate check. Gemini may generate identity/review/group content, never price.
- **Item specifics / listing profiles:** the current sports-card profile uses YP1.4 category `261328`; Basketball/Baseball bucket profiles deterministically supply their trusted group `Sport` while contradictory child metadata blocks. Persist variation metadata separately; group aspects contain only truthful common/profile values; omit heterogeneous optional/recommended values; only custom `Card` may vary as an eBay pivot. Future non-sports profiles must bring a separately validated eBay category/common-aspect contract rather than inheriting `261328` or an invented `Sport`.
- **Remote snapshots/order:** complete group snapshots only. Application selector order is authoritative; reconcile eBay `variantSKUs` by exact membership, not response order.
- **Media:** Media IDs are opaque and validated by trusted eBay URI boundary. Inventory cleanup does not imply Media deletion; current EPS resources may expire naturally.
- **Quantity/cleanup:** eBay remains authoritative for live quantities; historical captured copy rows never determine which copy sold. Active quantity adjustments use only the cumulative-counter delta applied to fresh remote eBay reads. **Quantity zero alone is NOT removal** and remains restockable. **Only already-zero** confirmed child Inventory Item AND Offer may be voluntarily removed with fresh proof at staging and again at execution; there must be no pending positive counter delta and at least two surviving children. Removal must NEVER zero available stock itself. Keep only minimal integrity-critical state proven necessary for crash recovery and future survivor publication; no generic local order tracking. - **Orders/sales:** eBay Seller Hub is the direct source of truth for orders, sales history, fulfillment, cancellations, returns, and refunds. YP8.1 Sandbox evidence proved that a specific child SKU is purchased correctly; that evidence is retained as validation, not as a mandate for local order ingestion. Recovery remains a small crash-safe frozen-revision/checkpoint journal—no generic event sourcing/workflow engine/resource registry/timeline/multi-tenant or speculative concurrency framework.

Dedicated variation persistence remains namespaced.
